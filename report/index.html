机器人 Agent Harness：现状与缺口Robot Agent Harnesses: Where the Field Stands

现在的机器人 Agent 大多支持调用 ROS 技能或 VLA 策略，但两类都接、还能根据实时的环境和任务状态决定用哪个的项目很少。 Most robot agents today can call either ROS skills or VLA policies. Very few connect both and decide which one to use from the live environment and task state.

3D 场景图（HoloAgent-0）、带位姿的观测（DimOS）、场景摘要 + 工具经验（Thea）、多机共享记忆（RoboOS）。 3D scene graphs (HoloAgent-0), pose-stamped observations (DimOS), a scene brief with tool experience (Thea), and memory shared across robots (RoboOS).

03 · 缺口the gap

能在 ROS 和 VLA 之间切换的很少Few can switch between ROS and VLA

深拆样本里，HoloAgent-0 有 ROS 也有学习模型，但每个技能绑死一个后端；Thea 能在几个 VLA 之间挑，但不涉及 ROS。在同一任务中按实时环境和执行状态切换两者的，目前还没有成熟的公开实现。 Among the deep dives, HoloAgent-0 has ROS and learned models but binds each skill to one backend; Thea picks among several VLAs but has no ROS side. No public implementation yet switches between the two within one task based on live environment and execution state.

02Landscape

横轴：动作主要靠确定性的 ROS 技能，还是学习型的 VLA 策略来执行。纵轴：Agent Runtime 深度，也就是 harness 在状态获取、记忆、验证、诊断和恢复上做了多少。大多数项目只在一头做得深，两类后端都接、闭环也做全的很少。 Horizontal axis: whether actions run mainly on deterministic ROS skills or learned VLA policies. Vertical axis: agent runtime depth, i.e. how much the harness does for state access, memory, verification, diagnosis and recovery. Most projects go deep on one end; few connect both backends and close the loop.

本次调研的核心判断Central finding

把 ROS 和 VLA 都包成 Skill 给 LLM 调用，部分项目已经能够做到。当前缺口主要集中在什么时候用哪个、两者怎么交接、执行中怎么盯、失败了怎么恢复、状态怎么获取和更新，以及怎么根据以往的执行结果调整选择。 Some projects can already wrap both ROS and VLA as skills an LLM can call. The gap lies in what comes next: when to use which, how to hand over between them, how to watch execution, how to recover from failure, how to obtain and update state, and how to adjust choices based on past runs.

Thea

照着 coding agent 的做法做机器人：VLA 策略当工具调用，场景图放进上下文，每步动作由评估器判定成败。 Built the way coding agents are: VLA policies are called as tools, the scene graph goes into context, and an evaluator judges each action.

VLA 即工具VLAs as tools 评估器Evaluator 工具经验Tool experience

核心机制Core mechanism

LLM 每轮只调用一个工具，工具背后是封装好的策略（π0.5、ACT、LingBot-VLA）；每个动作后由 VLM 评估器返回“成功 / 失败 / 进行中”。 The LLM makes one tool call per turn over wrapped policies (π0.5, ACT, LingBot-VLA). After each action a VLM evaluator returns success / failure / in-progress.

直接启发Direct lesson

唯一把 VLA 当一等工具、并有实测验证器（准确率 93.3%）的系统。 The only system with VLAs as first-class tools and a measured verifier (93.3% accuracy).

局限Limitations

没有显式规划；选哪个策略全靠 LLM 读工具描述；评估器带来延迟；不涉及 ROS。 No explicit plan. Policy choice is left to the LLM reading tool descriptions. The evaluator adds latency. No ROS.

Hi-VLA Design Study

VLM 规划器编排 VLA 控制器时，哪些设计真正重要：一项受控消融研究。 What matters when a VLM planner orchestrates VLA controllers: a controlled ablation study.

VLM → VLA 消融Ablation ALOHA

研究问题Research question

在仿真和真实 ALOHA 上，消融规划器推理、VLA 可控性、观测形式、记忆与终止条件。 Ablates planner reasoning, VLA steerability, observation format, memory and termination, in simulation and on a real ALOHA.

硬数据给出的答案What the numbers say

有硬数据：长程任务 67.08% vs 25.30%（扁平 VLA）；成功检测是最好的终止方式，由 VLM 判定终止最差。 Hard numbers: 67.08% vs 25.30% (flat VLA) on long-horizon tasks. Success detection is the best termination rule and VLM-decided termination the worst.

局限Limitations

只有 VLA：没有 ROS 分支、没有导航、没有世界记忆。 VLA-only: no ROS branch, no navigation, no world memory.

04缺口与 RoboClaw 方案04The gap and RoboClaw’s approach

前面的项目已经表明，ROS、经典控制器和 VLA 可以被统一封装成 Skill，甚至在同一任务中组合使用。当前更明显的缺口是： 系统如何根据任务、环境和执行反馈选择合适的执行方式，如何在不同执行器之间可靠交接，并通过验证与恢复形成闭环。 RoboClaw 主要针对这一层展开。 Across the projects above, the missing piece is consistent: no system yet switches between ROS and VLA within one task based on live state, then checks whether the switch worked. Below: first the problem, then how RoboClaw approaches it.

一 · 问题出在两类后端的衔接上1 · The problem is in combining the two backends

把 ROS 和 VLA 封装成 Skill 给 LLM 调用，部分项目已经能够做到。真正困难的是： 在什么情况下应该使用哪种执行方式、两者如何交接，以及执行过程中如何判断是否需要继续、恢复或切换。 ROS、VLA 都可能在底层“执行成功”后仍未完成真正的任务目标，因此 RoboClaw 不直接相信执行器自身的返回结果， 而是在 Skill 层统一检查实际结果。验证结果随后用于决定继续执行、重试、重新观察、切换执行器或重新规划。 Some projects already wrap ROS and VLA as skills for an LLM. Of the hard problems listed in §02, verification is the sticking point: checking whether each one finished, and did it right, works completely differently. For ROS you can compute pose error or read joint state; a VLA has no clear end signal, so an external detector has to judge. Without knowing when a VLA is degrading, there is no way to know when to switch.

二 · 现有系统怎么处理2 · What existing systems do

五个深拆样本都没有在运行时决定用哪个后端：有的在设计时就定死了，有的让 LLM 自己判断，有的本来就只有一种后端。 None of the five deep dives decides at runtime which backend to use: some fix it at design time, some leave it to the LLM, and some only have one backend.

  • HoloAgent-0固定Fixed 每类技能在设计时绑定一个后端。Each skill type maps to one backend at design time.
  • RoboOS另有侧重Elsewhere 它选择的是“哪台机器人”，而不是“哪种后端”。It chooses which robot, not which backend.
  • Thea隐式Implicit 由 LLM 根据工具描述与经验笔记选择策略工具。The LLM picks a policy tool from descriptions and experience notes.

需要回答的问题The question to answer

Agent 怎样在 ROS 和 VLA 之间选对执行方式、在任务中途切换，出错能恢复，并随时更新对环境的认识？ How can an agent pick the right one of ROS and VLA, switch between them mid-task, keep watch on execution, recover from errors, and keep its picture of the environment up to date?

三 · RoboClaw3 · RoboClaw

RoboClaw 不将后端选择简单交给 LLM 根据 Prompt 临时判断，而是将其作为 Runtime 中独立、可追踪的执行决策。Agent 按需查询环境、机器人状态和历史经验，由 Runtime 选择合适的执行方式，并记录选择依据；执行结束后，再通过验证结果判断该决策是否有效，并将结果反馈到后续选择中。我们的目标是构建一个能够长期运行的机器人 Runtime：按需理解环境，可靠组织和执行任务，验证实际结果，并通过持续积累的执行经验逐步提高稳定性。 RoboClaw doesn’t leave “which backend” for the LLM to settle inside a prompt. The runtime makes that decision as a separate step: each choice is logged with its reasons and can be replayed; it decides from the state queried on demand, and uses the verification result afterwards to check the choice. What we want is a robot runtime that can run long tasks: remember its surroundings, pick the right way to execute, check the results, and get more reliable from past runs.

状态按需获取State on demand 没有固定脚本把所有信息一次塞给 LLM。LLM 根据环境和任务，自己选工具查所需的状态，例如关节状态、时间记忆、空间记忆，汇总后再执行任务。 No fixed script dumps everything into the LLM. The LLM picks tools to query the state the task needs, such as joint states, temporal memory or spatial memory, then combines them before acting.
安全靠硬约束，不靠 LLMSafety by hard constraints, not by the LLM LLM 只下 pick object、move to room 这类高层指令；安全由 Skill Runtime 里的硬约束保证（例如限位、限速、碰撞检查），不依赖 LLM 判断。 The LLM issues only high-level commands such as pick object or move to room; safety is enforced by hard constraints in the skill runtime (e.g. joint and speed limits, collision checks), never by LLM judgment.
RoboClaw 的特点：主动切换。ROS 和 VLA 不只是二选一。例如 VLA 因环境干扰（光照、遮挡、物体偏离常见位置）表现下降时，Runtime 先切到 ROS 调整机器人位姿、相机视角或物体摆放，让任务回到 VLA 熟悉的训练条件，再交还给 VLA 继续执行。 What sets RoboClaw apart: active switching. ROS and VLA are not just alternatives. When a VLA degrades under environmental noise (lighting, occlusion, an object away from its usual pose), the runtime switches to ROS to adjust the robot’s pose, the camera viewpoint or the object’s placement, bringing the task back to the VLA’s training conditions, then hands control back to the VLA.

总体方向：General direction:LLM 按需查询状态、下达高层指令；Runtime 负责路由、在硬约束内混合执行 ROS/VLA、验证诊断与恢复，并从经验中演化，串成一个闭环。the LLM queries state on demand and issues high-level commands; the runtime handles routing, hybrid ROS/VLA execution within hard constraints, verification, diagnosis and recovery, and evolves from experience, all in one closed loop.

关节状态、3D 空间记忆、时间记忆、对象信息都做成可查询的工具，LLM 按任务自己选、自己汇总。Joint states, 3D spatial memory, temporal memory and object info are exposed as query tools; the LLM picks and combines what the task needs.

02

组织任务Organize

LLM 只下 pick object、move to room 这类高层指令；Skill Graph 表达依赖、分支、并行和资源约束。The LLM issues only high-level commands such as pick object or move to room; skill graphs express dependencies, branches, parallelism and resources.

03

选择与切换Choose & switch

按几何、接触、风险和历史表现选后端；执行中按实时状态切换，必要时用 ROS 为 VLA 恢复熟悉的条件。两类后端都在 Skill Runtime 的硬约束内运行。Pick the backend from geometry, contact, risk and track record; switch mid-task on live state, using ROS to restore conditions the VLA knows. Both run inside the skill runtime’s hard constraints.

04

验证、诊断与恢复Verify & diagnose

动作完成由证据判断；失败时先自检、查日志定位原因（参考 ROSA），再决定重试、重观察、重规划、切换后端或请求协助。Evidence decides completion; on failure, self-inspect and read logs to find the cause (as in ROSA), then choose retry, re-observation, replanning, backend switching or assistance.

05

积累与演化Evolve

从执行记录提取 Skill Experience，生成候选技能，经评测后再替换旧版本。Extract skill experience from traces, propose candidates and promote them only after evaluation.
