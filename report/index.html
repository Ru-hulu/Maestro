机器人 Agent Harness：现状与缺口Robot Agent Harnesses: Where the Field Stands

现有机器人 Agent 大多只接入确定性 ROS 技能或学习型 VLA 策略中的一类；同时接入两类后端，并能依据实时环境与任务状态在二者之间选择的系统仍属少数。 Most robot agents integrate only one of two backends: deterministic ROS skills or learned VLA policies. Few integrate both and choose between them according to the live environment and task state.

01概览01Overview

为什么需要 HarnessWhy a harness

VLA 任务失败，很多时候并不只是因为模型能力不足，而是缺少执行过程中的监督与纠错机制：动作完成后无人验证，失败后缺乏原因诊断，环境发生变化时，也没有机制将机器人重新调整到模型熟悉的状态。Harness 的作用就是补上这一层执行与管理能力，其带来的收益大致可以归纳为四点： When a robot fails to get something done, the model is often not the problem — nothing is watching. No one checks that the action actually finished, no one asks why it failed, and when the scene changes no one puts the robot back into a state the model knows. A harness is that missing layer, and it buys roughly four things:

  • 针对环境变化，先把机器人和视角调回策略熟悉的条件再执行，不必重新训练模型。 When the scene changes, the robot and its viewpoint are moved back to conditions the policy knows before it runs — no retraining needed.
  • 动作算不算做完，由外部检查给出证据，而不是执行器自己判定成功。 Whether a step is done is settled by an outside check, not by the executor declaring success.
  • 机器人的状态、感知到的环境、完成的内容提供都可以查，LLM 按需要取用。 The robot’s state, what it has seen and what it has done all stay queryable, and the LLM takes what it needs.
  • 失败会留下原因和过程，下一次不必从头试起。 Failures leave behind a cause and a trace, so the next attempt does not start from scratch.

深度样本都把机器人能力封装成 skill，由 LLM 循环调用。区别主要在动作单元：skill graph、子任务、单次 tool call、MCP skill，以及解析式原语与 VLA 原语。 The deep-dive systems wrap robot capabilities as skills under an LLM loop. The unit of action differs: a skill graph, a subtask, a single tool call, an MCP skill, or an analytic or VLA primitive.

记忆是主要差异点Memory is the differentiator

3D 场景图（HoloAgent-0）、带位姿的观测（DimOS）、场景摘要 + 工具经验（Thea）、多机共享记忆（RoboOS）、从执行记录提炼的任务与全局记忆（Harness VLA）。 3D scene graphs (HoloAgent-0), pose-stamped observations (DimOS), a scene brief with tool experience (Thea), memory shared across robots (RoboOS), and task and global memory distilled from execution traces (Harness VLA).

03 · 缺口the gap

能在 ROS 与 VLA 之间切换的系统仍属少数Few systems can switch between ROS and VLA

在深入分析的样本中，HoloAgent-0 兼有 ROS 与学习模型，但每类技能在设计时绑定单一后端；Thea 可在多个 VLA 之间选择，但不含 ROS 后端；RoboOS 论文称技能库兼含两类工具并由 Agent 选择，但开源代码中未能核实。目前尚无公开实现能在真实机器人上由 Runtime 依据实时状态显式地在二者之间切换；最接近的 RPent 真机扩展（2026-09）仍由 LLM 按提示规则调度。RoboClaw 以主动切换为切入点（§04）。 Among the deep dives, HoloAgent-0 has both ROS and learned models but binds each skill type to a single backend at design time; Thea selects among several VLAs but has no ROS backend; the RoboOS paper states that its skill library holds both kinds of tools, chosen by the agent, which could not be verified in the open code. No public implementation yet has a runtime switch explicitly between the two on a real robot from live state; the closest, RPent’s real-robot extension (Sep 2026), still leaves the choice to LLM prompt rules. RoboClaw takes active switching as its entry point (§04).

对 RoboClaw 的启发Lessons for RoboClaw

  • 类型化 Skill Graph：每个节点带前置条件、状态和恢复边，失败时沿恢复边重试、重规划或询问用户。→ RoboClaw 的 Skill Graph 和恢复策略可以直接参考。 Typed skill graph: each node carries preconditions, status and recovery edges; on failure it retries, re-plans or asks the user along those edges. → A direct template for RoboClaw’s skill graph and recovery.

  • ROS 2 指令 / 状态总线：同一套 Agent 驱动 3 类机器人。→ RoboClaw ROS 侧 Skill Runtime 的参考实现。 ROS 2 command / status bus: one agent drives 3 robot types. → A reference for the ROS side of RoboClaw’s skill runtime.

架构主线Architecture in one line

大脑（RoboBrain）把任务拆成子任务，分发给各机器人的技能库；通过 Redis 共享记忆同步状态。 The brain (RoboBrain) splits a task into subtasks and dispatches them to per-robot skill libraries, keeping state in sync through Redis-backed shared memory.

突出之处Where it stands out

对 RoboClaw 的启发Lessons for RoboClaw

  • 一小套参数化 Skill：RoboSkill 示例只有 navigate_to_target(target)、grasp_object(object)、place_to_affordance(affordance, object) 三个。→ RoboClaw Skill 集的设计原则。 A few parameterized skills: the RoboSkill example has only navigate_to_target(target), grasp_object(object) and place_to_affordance(affordance, object). → The design rule for RoboClaw’s skill set.
  • Skill 描述里写明调用条件：例如“已经成功就不要再调用”，相当于给 LLM 的轻量前置条件。→ RoboClaw 可以在 Skill 定义里显式写前置 / 后置条件。 Call conditions in the skill description: e.g. “do not call once it has succeeded”, a lightweight precondition for the LLM. → RoboClaw can make pre/post-conditions explicit in each skill definition.
  • High / Low level 分离：大脑只做规划和调度，小脑执行技能，Redis 共享记忆同步状态。→ 对应 LLM 只下高层指令、Skill Runtime 负责执行。 Brain / cerebellum split: the brain plans and schedules, the cerebellum runs skills, and Redis-backed shared memory keeps state in sync. → Matches “the LLM issues high-level commands, the skill runtime executes”.

04缺口与 RoboClaw 方案04The gap and RoboClaw’s approach

本节首先界定 ROS 与 VLA 两类执行后端的衔接问题，继而梳理现有系统的处理方式，最后提出 RoboClaw 的设计，其核心是围绕 VLA 调用的主动切换。 This section defines the problem of coordinating the ROS and VLA backends, reviews how existing systems handle it, and then presents RoboClaw’s design, centred on active switching around VLA calls.

一 · 问题界定：两类后端的衔接1 · Problem: coordinating the two backends

将 ROS 技能与 VLA 策略统一封装为 LLM 可调用的 Skill，已有系统能够做到；尚未解决的是二者的协同，可分解为四个子问题：后端选择，即何种任务与环境条件下采用何种执行方式；交接，即控制权与状态如何在两类后端之间可靠传递；执行监控，即如何获取并更新环境与执行状态，据此判断继续、恢复还是切换；经验利用，即如何依据历史执行结果修正后续选择。此外，两类后端都可能在底层报告“执行成功”而实际未达成任务目标，因此执行器自身的返回值不能作为完成的依据。 Existing systems can already wrap ROS skills and VLA policies as skills an LLM can call. What remains unsolved is their coordination, which decomposes into four sub-problems: backend selection, which execution path suits which task and environment conditions; handover, how control and state pass reliably between the two backends; execution monitoring, how to obtain and update environment and execution state and decide from it whether to continue, recover or switch; and use of experience, how past outcomes should revise later choices. Moreover, either backend can report “success” at the low level without achieving the task goal, so an executor’s own return value cannot serve as evidence of completion.

RoboClaw 要回答的问题The question RoboClaw must answer

在同一任务中，如何依据实时状态协调 ROS 与 VLA，使二者互为补充，而非相互替代？ Within one task, how can ROS and VLA be coordinated from live state so that they complement rather than replace each other?

三 · RoboClaw3 · RoboClaw

RoboClaw 不将后端选择交由 LLM 在 Prompt 内临时判断，而将其作为 Runtime 中独立、可追溯的执行决策：决策依据（环境状态、机器人状态与历史表现）连同决策理由一并写入时间记忆；执行结束后，由验证结果评估该决策，并反馈至后续选择。 RoboClaw does not leave backend selection to an ad-hoc judgment by the LLM inside the prompt; it treats selection as an independent, traceable execution decision in the runtime. The inputs to each decision (environment state, robot state and track record) are written to temporal memory together with its rationale, and after execution the verification result evaluates the decision and feeds back into later choices.

核心设计 · 主动切换Core design · Active switching

ROS 与 VLA 并非二选一。VLA 对相机视角与机器人初始状态最为敏感，小幅扰动即可使成功率由 95% 降至 30% 以下（LIBERO-Plus）；而对机器人本体与机载相机而言，这两个因素恰好都能由 ROS 精确设定并加以验证，这正是切换发挥作用之处。 ROS and VLA are not alternatives. VLAs are most sensitive to camera viewpoint and robot initial state: modest perturbations drop their success rate from 95% to below 30% (LIBERO-Plus). For the robot body and its onboard cameras, both factors are exactly what ROS can set precisely and verify, which is where switching pays off.

起始条件Start state
每个 VLA Skill 声明其起始条件：机械臂初始构型、底盘相对目标的位姿，以及机载相机（头部、腕部或底盘相机）相对工作区的位姿。对在自有示教数据上微调的 VLA，这些量取自示教首帧的统计范围，而非单一位姿。固定的第三人称相机无法由机器人调整，只能在部署时保持与训练时一致。 Each VLA skill declares its start condition: the arm’s initial configuration, the base pose relative to the target, and the pose of onboard cameras (head, wrist or base) relative to the workspace. For a VLA fine-tuned on our own demonstrations, these are ranges taken from the first frames of the demonstrations rather than a single pose. Fixed third-person cameras cannot be adjusted by the robot and must simply match their training placement at deployment.
分工Roles
LLM 通过 ROS 技能执行对位；Runtime 以代码检查起始条件（例如经 TF 测得的位姿误差是否落在声明范围内），不满足则拒绝调用 VLA；执行中若评估器判定进展停滞或失败，由 Runtime 触发切回 ROS 重新对位，再交还 VLA，每次决策连同依据写入时间记忆。与提示词规则的区别不在于规则写在哪里，而在于由 Runtime 强制执行、可以复现，不依赖 LLM 是否遵守。 The LLM performs the alignment through ROS skills; the runtime checks the start condition in code (for example, whether the pose error measured through TF falls within the declared range) and refuses to call the VLA if it is not met. If the evaluator reports stalled progress or failure during execution, the runtime switches back to ROS to re-align before the VLA resumes, and every decision is written to temporal memory with its inputs. What differs from prompt rules is not where the rule is written but that the runtime enforces it reproducibly, rather than relying on the LLM to comply.
扰动示例Perturbation
若示教数据中目标多出现在左前方，VLA 会习得与之匹配的接近与抓取轨迹；测试时目标被换到右侧，冻结的 VLA 仍可能沿用原有空间先验，去到错误位置、抓空，或以不合适的姿态起手。此时由 LLM 调用 ROS 先把底盘与机械臂带回声明的起始条件内，VLA 只负责最后的抓取。 If demonstrations mostly place the target at the front left, the VLA learns approach and grasp trajectories to match. Swap the target to the right at test time and the frozen VLA may still follow that spatial prior — reaching the wrong place, closing on nothing, or entering from an unsuitable pose. The LLM then drives ROS to bring the base and arm back inside the declared start condition, and the VLA performs only the grasp.
相关工作Prior work
Harness VLA（§03）在仿真中由规划器调用解析式原语为冻结 VLA 重新摆位，加上这套 harness 后，同一 VLA 在 LIBERO-PRO 上的成功率由 50.0% 提升到 82.4%；其代码库 RPent 的双臂 Franka 真机扩展（2026-09）由 LLM 按提示规则调度，相机固定，也未声明起始条件。RoboClaw 的不同在于：起始条件显式声明、由 Runtime 强制检查，并覆盖机载相机视角，基于 ROS 技能栈实现。 Harness VLA (§03) has a planner re-stage a frozen VLA with analytic primitives in simulation; with this harness, the same VLA rises from 50.0% to 82.4% on LIBERO-PRO. Its codebase RPent’s dual-Franka real-robot extension (Sep 2026) schedules by LLM prompt rules, with fixed cameras and no declared start condition. RoboClaw differs in declaring the start condition explicitly, having the runtime enforce it, covering onboard camera viewpoint, and building on a ROS skill stack.
核心设计 · 重试即数据Core design · Retries as data

一次任务中的反复尝试本身就是带标签的数据。RoboClaw 将每次尝试的状态、决策、LLM 的推理（为何这样选、为何判定失败）与验证器给出的结果写入同一条记录：向前用于下一次决策，向后即可作为持续学习与强化学习的训练样本。 Repeated attempts within one task are already labelled data. RoboClaw writes each attempt’s state, decision, the LLM’s reasoning (why this choice, why this was judged a failure) and the verifier’s outcome into one record: forward, it informs the next decision; backward, it is a training sample for continual and reinforcement learning.

记录内容Recorded
每次尝试写入一条记录：环境与机器人状态、所选后端与参数、推理与理由、验证证据、结果。失败原因取自 ROSA 式自检与日志，而非模型自述。同一任务内的多次重试按时间串成一条轨迹，与该任务的时间记忆同源。 Each attempt writes one record: environment and robot state, chosen backend and parameters, reasoning and rationale, verification evidence, outcome. Failure causes come from ROSA-style self-inspection and logs rather than the model’s own account. Retries within a task are chained by time into a trajectory, held in the same temporal memory as the task itself.
两个用途Two uses
在线：检索相似情境下的历史记录，修正后端选择与起始条件范围，即本节一中的“经验利用”。离线：以验证器证据为奖励信号，同一情境下成功与失败的重试天然构成对比样本，可用于离线强化学习与偏好学习；记录中的推理文本则可用于蒸馏与微调。二者共用一份记录，不需要为训练单独埋点。 Online: retrieve records from similar contexts to revise backend choice and start-condition ranges — the “use of experience” sub-problem above. Offline: verifier evidence serves as the reward signal, successful and failed retries in the same context form natural contrastive pairs for offline RL and preference learning, and the recorded reasoning supports distillation and fine-tuning. Both uses read one record; no separate instrumentation is added for training.
前提Requires
奖励的可信度取决于验证：执行器自报成功不能作为标签，标注一律取自评估器证据。记录须可复现：状态快照、技能版本与参数一并保存，否则无法离线重放，样本也无法归因到某一次决策。 The reward is only as trustworthy as the verification: an executor reporting success is never a label, and every label comes from evaluator evidence. Records must be replayable — state snapshots, skill versions and parameters are stored alongside, or a sample can be neither replayed offline nor attributed to a particular decision.

总体设计：Overall design:LLM 按需查询状态并下达高层指令；Runtime 负责后端选择、在硬约束内执行 ROS 与 VLA、验证与恢复，并从执行经验中持续改进，五个环节构成闭环。the LLM queries state on demand and issues high-level commands; the runtime selects backends, executes ROS and VLA within hard constraints, verifies and recovers, and improves from experience. The five stages form a closed loop.

01

按需获取状态Query state

关节状态、3D 空间记忆、时间记忆与物体信息均以查询工具提供，由 LLM 按任务选取与组合，而不预先写入 Prompt；返回结果附带置信度、新鲜度与来源，据此决定直接使用还是重新观测。Joint states, 3D spatial memory, temporal memory and object information are exposed as query tools that the LLM selects and combines per task, rather than being preloaded into the prompt. Each result carries confidence, freshness and provenance, which determine whether it is used directly or re-observed.

02

组织任务Organize

LLM 仅下达 pick、move_to 等高层指令，由一小套正交、参数化的 Skill 组合完成任务（参考 RoboOS）；Skill Graph 表达依赖、分支与资源约束，计划阶段支持人工确认与修改。The LLM issues only high-level commands such as pick or move_to, and tasks are composed from a small set of orthogonal, parameterized skills (after RoboOS). A skill graph expresses dependencies, branches and resource constraints, and people can confirm or edit the plan before execution.

03

选择与切换Choose & switch

依据目标几何、接触特性、风险与历史表现选择后端；VLA 调用前由 ROS 完成起始对位，执行中按状态切换。两类后端均在 Skill Runtime 的硬约束（限位、限速、碰撞检查）内运行，安全不依赖 LLM 判断。Choose the backend from target geometry, contact, risk and track record; ROS performs start alignment before each VLA call, and execution switches on live state. Both backends run inside the skill runtime’s hard constraints (joint and speed limits, collision checks), so safety never depends on LLM judgment.

04

验证、诊断与恢复Verify & diagnose

以证据判定动作是否完成；失败时先自检并查询日志定位原因（参考 ROSA），再选择重试、重新观测、重新规划、切换后端或请求协助。Completion is judged from evidence. On failure, the runtime self-inspects and reads logs to locate the cause (as in ROSA), then chooses among retry, re-observation, replanning, backend switching and asking for help.

05

积累与演化Evolve

执行记录与 LLM 的推理（为何如此规划、为何选择该后端、为何判定失败）一并写入时间记忆，可按时间检索与回放；从中提炼 Skill 经验并生成候选技能，经评测后再替换旧版本。同一批记录也是训练数据：以验证器证据为奖励，可用于离线强化学习与推理蒸馏（重试即数据）。Execution traces and the LLM’s reasoning (why this plan, why this backend, why a step was judged a failure) are written to temporal memory, where they can be queried and replayed by time; skill experience is distilled from them, and candidate skills replace old versions only after evaluation. The same records are training data: with verifier evidence as the reward, they support offline RL and reasoning distillation (retries as data).

04 ·单独做一个选后端的模块，每次选择都能查04 ·A separate module that picks the backend, with every choice on record

复用现有系统已经验证的模块，把隐式或固定的后端选择推进为显式、可记录、可验证的路由层。 Reuse modules already validated by existing systems, then turn implicit or fixed backend choice into an explicit, logged and verifiable routing layer.
